# 云端多用户架构改造计划

**状态：**方案评审稿；尚未获批准、尚未实施。

## 目标与边界

保留 SillyTavern 1.19.1 上游的每用户文件目录、HTTP/API、扩展读写的路径语义、聊天 JSONL 格式、用户 ZIP 与清除流程。在单实例、单权威 `dataRoot` 前提下，逐步改善新开户默认资源的实际磁盘块占用、启动与登录后首屏等待、生成前 tokenizer 往返，以及账户/头像列表的数据成本。SQLite 只计划替代核心账户记录；不把它误当成多实例并发协议。

“完全兼容”在本稿中指官方接口、扩展上下文和每用户文件路径/文件读写语义兼容。`_storage` 中私有 `user:` / `avatar:` 键不是第三方接口承诺；迁移前应公告。原列表接口默认继续返回旧 base64 响应，内置前端使用显式分页资料/有权限头像路径。

性能计划先建冷/热基线，不把静态分析结论写成服务器耗时。资源开户放行标准为：在经验证支持 CoW 的隔离卷上，为 300 个合成空白账号播种，默认种子的新增物理数据块相对普通复制至少降低 90%，并且每账号文件内容、路径与用户 ZIP 条目均一致。不支持克隆的卷自动回退普通复制并记录状态；这类卷不宣称获得节省。

## 已核实的现状

- 新账号开户时会立即播种默认内容。仅按当前跟踪的发行种子计，每账号 191 个文件、16,134,731 字节（15.39 MiB）；其中背景、角色立绘及角色卡约占 98.79%。300 个独立副本约 4.51 GiB，500 个约 7.51 GiB，不含其他用户数据及文件系统分配误差。
- 典型应用入口读取/写入路径为 `dataRoot/<handle>/...`。删除、改名、用户自定义背景、设置与 ZIP 均有各自普通文件语义。硬链接不兼容独立写入、备份和清除；Overlay/whiteout 并非当前 ZIP 及目录清除的透明替代。
- `node-persist` KV 中 `values(prefix)` 会先全量打开和解析目录项再筛选。账户管理分页在内存全扫之后才发生；头像还作为内联 base64 出现在列表视图中。独立图像响应不会自动解决账户 KV 的全扫。
- 隐匿登录会短路公开列表存储读取；目前登录初始化仍逐次获取 CSRF 和公开列表状态。账户页同时存在设置、当前账户、扩展、角色和欢迎区等等待阶段，Webpack 首次构建在监听前发生。遮罩退场、可操作、欢迎区可见及 `APP_READY` 是不同的测量事件。
- 生成链中 OpenAI 消息计数可按消息逐条 `await` 远端计数；世界书预算计数使用按顺序累计的文本前缀，关联到实际上下文截断。字符/编辑器或 token 编辑器计数不能未经确认统称为生成热链。
- 账户记录为 SHA-256 文件名封装 JSON；头像分离在 `avatar:` KV。账户实例 ID 绑定会话、清除和备份身份。清除任务与备份任务保存于其他路径，不等于账户 KV。现有用户 ZIP 只含用户目录，不是账户库/整站灾备。
- `getUserDirectories()`、`request.user.profile/directories`、私有 Router 挂载、操作追踪及 `accountId` 是需要每次同步上游显式审查的兼容接点。同名 API 的请求/响应曾由 fork 改变，不可假设上游兼容。

## 设计原则

1. 以 Git 跟踪的上游 `82b64a45` 为同步基准。避免重写通用用户目录文件处理；将共享种子、账户存储、token 计数与头像读取分别封装在内部深模块中。
2. 继续只支持单个活动写入者。独立 `dataRoot` 在同一进程/同一单实例部署上权威；反代多工作进程、容器副本数增加和网络文件系统不视为受支持的扩展。采用内置 SQLite 后，云端多用户受支持运行时限定为 Node 22.13+（生产建议 24）；Bun/Deno 脚本不构成此部署模式的兼容承诺。
3. 保持用户路径、独立可写普通文件、JSON/JSONL、扩展 API、上传、下载和删除契约。绝不把硬链接当 CoW，也不让共享模板接受用户可写权限。
4. 保留旧账户列表原响应供未迁移调用方；只有经过筛选和分页的新版管理请求和授权单图请求进入低字节路径。隐匿登录只改变未登录公开账号列表，不改变管理员列表权限。
5. 不因优化牺牲精确 token 数和扩展激活顺序。批量化只改变传输形状，不改变各 tokenizer 的分项计数、预算/合并规则与顺序处理。
6. 每一阶段能独立度量、停止和恢复。迁移使用范围受限的可逆 journal，不复制整份 `dataRoot`；在约 80 GB 数据盘已使用 70 GB 的场景，迁移工具不得再要求同卷空出 70 GB。每阶段实施前都按实际 source size 及事务/临时文件上界做可用空间预检；不够就不写入。完整灾备应放到其他设备/对象存储，不能计入同卷回退机制。

## 分阶段清单

### 0. 建立基线和同步闸门

- 记录当前 `HEAD`、Node 22.13/24、OS/文件系统、卷/容器挂载方式和源码版本。使用合成租户，不扫描或修改实际用户目录。
- 固定 50/300/500 个合成空白账号、50/500 个合成角色库、不同历史消息数与世界书命中数的冷/热场景。
- 登录分别记录 CSRF、公开列表、表单可操作、登录导航；首屏分别记录遮罩退出、欢迎区可见、`APP_READY`。记录每端点 TTFB/响应字节/请求数、ESM 最深发现链、长任务和 P50/P95。
- tokenizer 场景按 API、模型、tokenizer、消息数、提示长度记录生成前远端请求数、cache miss/hit、重复并发 miss、P50/P95；保存最终 token 分项、选用历史消息和世界书条目的确定性样本。
- 头像管理使用 300 个合成用户，分别测用户分页首次 JSON 字节、头像源文件读取次数、单图字节、翻页后请求数和操作延迟。把过滤/KV扫描成本与 base64 传输成本分开。
- 将新兼容断言加进隔离验收入口，但不先修改产品逻辑。记录上游同名路由和活跃扩展直接使用文件路径及账户键的静态盘点范围。

### 1. 新账户默认素材文件级 CoW

- 构造只读发行清单：源相对路径、字节数、SHA-256、资产类别、seed 版本。只纳入当前内容索引实际播种到每个用户目录的文件；全局错误/样式资源和不应租户化的目录单独排除。
- 在当前 `dataRoot` 的私有位置建立版本化、只读的完整 seed master，验证权限、manifest 和完整性。母版不接受租户请求写入；更新发行版时原子发布新版本，保留仍被账户 content ledger/迁移引用的旧版本。
- Node `COPYFILE_FICLONE` 会在支持时尝试 CoW 并在不支持时普通复制成功，但不报告每个目标是否 CoW；`COPYFILE_FICLONE_FORCE` 则可能拒绝完整写入并把探针/fallback 留给应用处理。先对两个标志各自做 Linux/Windows 原型，再决定播种模式；不支持错误清单必须基于实测，权限、空间不足、来源读取和完整性错误不能伪装成 fallback。每个普通文件仍需临时目标、字节校验和同目录原子改名；不对目录/符号链接应用未经验证的 clone 语义。硬链接禁止作为 fallback。仅“函数成功”不证明 CoW；通过独立卷同文件系统能力探针、运行期成功/回退计数及物理 allocated-block 对照报告节省量。
- 并发开户以现有账号锁为基础，确保同一目标目录只完成一次播种；崩溃时部分文件可安全重入，已存在目标不覆盖。开户前计算 CoW 探测结果；若会回退普通复制，预先检查 dataRoot 当前可用空间能否容纳该用户整份 manifest 种子和安全余量，不足则拒绝新建且清理本次未提交的空目录/元数据，并报告错误。检查后台种子巡检、普通补种、开户触发的强制类型与用户已删除默认资源语义保持不变。
- 新增 seed master 前用 `statfs`/同等能力检查当前卷可用空间，仅在 manifest 母版增量、journal/temporary clone 和安全余量全部可容纳时发布；不给现有 70 GB 用户目录做副本。先验证 20 账号功能和 failure injection，再上 300 账号物理块对照。只有在可量化支持 CoW 的隔离文件系统上达成 90% 指标并通过 ZIP/权限/上传覆写/用户删除测试，才推进此项生产功能。
- 存量工具必须停服，先输出 dry-run CSV/JSON：逐账号/路径/逻辑字节、目标版本哈希、候选/跳过原因、链接数、设备号和已登记状态。仅精确匹配可信种子哈希且为普通单链接文件的目标可候选；用户修改、哈希不符、硬链接、符号链接、异常权限或状态不明一律不触碰。正式工具先在原位置同目录 rename 原文件（保留 inode、无数据块副本），强制 CoW 到临时路径、校验 hash，再原子替换并记录 journal；首错停止可用 rename 恢复原文件。clone 不支持时跳过整项，不用普通复制；任一步需额外数据块而预检不满足则零修改退出。CoW 克隆不是灾备。

### 2. 默认云端隐藏登录名单与轻量登录页

- 新增与 `default/config.yaml` 分离的云端部署配置模板，显式选择后新云端实例启用隐匿登录；不得更改上游/本地默认模板。模板要在 Linux/Docker 部署入口可选，安装已有数据根时不自动选择或覆盖运行配置。分别验证新云端实例、普通本地实例、升级已有 YAML、YAML 缺键补齐、环境变量覆盖与管理员显式选择；不得依赖配置升级中的 `defaultsDeep` 覆盖既有值。
- 登录页返回行为保持根路由、CSRF、会话及自动登录逻辑。隐匿登录分支不获取公开账号/头像数据；匿名访客仍可按原路由策略加载登录文档，但不能通过列表读取卡片资料。明确这只隐藏未登录登录列表，不改变管理员权限视图。
- 从 `login.html` 分离首页通用 CSS 的非必要依赖，只保留登录控件、可访问性和必要字体；表单可操作不等待头像。静态资源尽量沿用现有 URL 与顺序；不会无差别预加载整个 ESM 图，也不把动态租户扩展路由送到公共 CDN。
- 根据同一版本部署级输出验证是否可安全进程内缓存 `/version`；测试静态资源 gzip/Brotli、ETag/304 与 Cache-Control。没有内容哈希的动态 `/css/user.css`、个性化响应、CSRF、`/scripts/extensions/third-party/*` 不得获得跨租户公共缓存策略。CSP 先观测 Report-Only，另案评估，不并入加载改造。
- 验收首次绘制和可输入/提交的 P50/P95、请求瀑布、表单不被字体/外部背景拖延、`noauto` 和查询串行为；新安装隐藏公开列表，旧配置明确保持原模式。

### 3. 生成前 tokenizer 同源批量请求与隔离缓存

- 为内部客户端和 tokenizer 路由增加 OpenAI 消息批量计数入口；旧逐条接口保持原 URL、参数及响应。批量入口将所有请求关联到当前认证用户上下文，并限单批条数、总文本字节及请求体尺寸，逐条返回与当前单项接口一致的精确成本；不得把不同用户或后端合并一批。
- 前端生成链对原本逐条远端计数的独立消息一次发送批次，结果依原消息顺序回填和逐条应用预算。保留 message framing、name、tool、模型映射与 provider 规则；世界书继续以有序累计前缀精确计数，不把整段近似化或换成不等价本地 tokenizer。
- 去重相同文本的并发 in-flight miss，缓存键涵盖 tokenizer 类型、模型、provider/API 类型、远端 endpoint 身份和 accountId；切换用户、API endpoint、模型、tokenizer、padding 或删除 chat 后验证隔离/失效。不得记录用户 prompt 文本到遥测日志。
- 对 OpenAI、兼容 provider、Claude、Llama3、Kobold、TextGen 及本地 tokenizer 分别比较改造前后 count。最终 token 分项、最终提示消息、世界书集合及被截断历史边界要求完全相同；对远端故障/限流，沿用当前失败和预算行为。
- 验收热链 token API 往返数、总体生成前等待和 P95；与单项旧路由相比请求数应随批次下降，但不以牺牲计数等价作为性能优化。

### 4. 用户头像文件化与安全分页

- 新版头像首选用户目录内受控普通文件，限制像素/字节和解码格式；管理员列表始终不包含图片 base64，授权单图读取服务内同时支持尚未迁移的 archive KV fallback。旧 HTTP 接口上传的 data URL 在经过严格解码限制后写文件；空间不足则拒绝更新，不覆盖原图。当前旧账户头像存于全局 KV、不在用户 ZIP 中。迁移后，已文件化头像会作为普通用户文件进入 ZIP；尚在归档 fallback 的头像仍不在 ZIP 中。这是 ZIP 内容契约的变化，需在管理员/用户迁移公告中说明，并允许空间不足账号暂时使用旧头像读取但不导出头像。
- 账户 SQLite cutover **不解码、不复制头像图片**：旧 `avatar:` KV 文件同卷 rename 到 `_migration-legacy`，根据账户原 handle/SHA key 建立映射。新服务的头像读取先查用户目录文件，文件未迁移时按权限点读归档 KV 返回 data URL；这保留旧图而不同时占用解码后的图片空间。头像批量文件化另设 opt-in 离线任务，必须先测每张实际解码尺寸并按本次图片集合预检峰值；单张文件写入、hash 验证、原子改名后才释放相应旧 KV。空间不足时保留 base64 回退，不迁移该头像；无效数据立即记录详细错误并停止，不静默跳过。
- 提供授权的头像单图读取路径：管理员列表头像要求管理员会话与查询目标账户当前仍存在/未进入清除封锁；本人头像仅返回本人。使用单图内容 ETag、`private, no-store`；删除/改图改变版本标记；账号同名重建的 accountId 不复用旧缓存。公开登录名单默认不请求/返回头像。
- 管理员资料接口使用真实 SQL 筛选、确定性排序与分页，默认只回头像是否存在/版本，不读本页每张图；内置 UI 先取资料，图像元素进入可见区后才发单图请求，翻页/取消/关闭时废弃旧结果。旧 `/api/users/get` 不带新模式时保留 base64 contract；新版请求显式 opt-in 不返回图片字段，兼容用户需走有权限的新单图端点。
- 验收 300 个用户分页、资料 JSON 不含 base64、未授权单图请求拒绝、合成头像不串用户、头像改/删/停用/到期/清除/用户名复用路径、完整用户 ZIP 含本人头像且不含他人头像。

### 5. SQLite 账户权威表和停机升级工具

- Node 内置 `node:sqlite` 在 22.5 引入，22.13 只移除了实验性 CLI 开关，Node 24 仍不能在文档中称为稳定 API。启用账户 SQLite 前，维护者须明确接受实验 API 风险；否则本阶段改用成熟外部 SQLite 模块或延期。若接受内置方案，云端最低 Node 22.13、建议 24，仅承诺 Node 运行时；在单一 `account-store` Adapter 内封装 `DatabaseSync`、schema、预备语句、事务和错误映射。启用 WAL 的备份必须走 SQLite 一致性备份/checkpoint 协议，禁止在线裸拷贝 `.db` 作为快照。
- schema 保留原始 handle、规范化查询字段、name、创建/密码 salt/hash、角色、启停、邮箱、时间、唯一且稳定的 accountId、schema 版本与兼容状态。唯一约束应跟现有用户名比较/大小写语义严格对应；迁移前报告并阻止任何不能安全标准化的历史冲突，不擅自改名或重分配实例 ID。
- 将所有核心 `user:` 读写消费者切到 Adapter：启动初始化、创建、登录/自动登录、更新会话版本、Basic Auth、管理员/private/public 端点、恢复 CLI、生命周期、清除、备份和安全启动检查。把 `readUser/writeUser` 现有 seam 用于 lifecycle，其他写入走含 handle/accountId 校验的统一事务。账户关闭模式仍用原 `DEFAULT_USER` 语义，不能用数据库默认行替换。
- 以单实例文件锁保证同一 `dataRoot` 同时只有一个服务/迁移程序写入。服务启动校验文件锁和 schema；创建、账户变更、移除和实例 ID 条件更新使用 SQLite 事务。进程内文件操作仍通过现有用户操作跟踪；不声称跨主机或多 Node worker 支持。
- 编写显式离线迁移命令，包含 `--check/--dry-run`、`--apply` 和 `--rollback`。迁移前停应用、确认进程清零并取得 `dataRoot` 独占锁。因 node-persist 文件名是 key 的 SHA-256，工具需要枚举 `_storage` 中的 KV 文件并逐个解析 envelope 的 `key` 字段来找 `user:`/`avatar:`；一次只处理一个有大小上限的 envelope，释放无关 value，不把目录全部加载到内存，不调用 `node-persist.values()/keys()`。验证码、卡密、SMTP 等其它 KV 只读识别、不改写、不归档。账户与头像源 KV 在同卷 rename 到 `_migration-legacy`，该目录必须位于 `_storage` 同级，不能被 node-persist 的目录扫描当作 KV 项。用户目录、聊天、上传和完整 `dataRoot` 均不复制；种子只访问 manifest 登记的路径。拒绝超限 envelope、坏格式、重复/空 handle、无效/不唯一 accountId、重复目标或未知 schema。dry-run 输出相关条目数、实际字节/hash 摘要、SQLite 上界、最大 KV/头像/临时文件、transaction journal、同卷 rename、seed master 增量、有界日志和安全余量；按 `dataRoot` 所在卷实时可用空间计算峰值。空间不足或预估不确定时非零退出、零修改。

`--apply` 使用新 DB 临时路径、SQLite 显式事务和进度 journal/hash。旧账户及头像 KV 原始文件按 SHA key 文件名同卷原子 rename 到 `dataRoot/_migration-legacy`（与 `_storage` 同级），保留原始字节且不额外复制数据块，避免活动 `_storage` 前缀扫描继续载入账户 value。迁移器按源 envelope 和 SQLite 的 accountId/handle 建立 archive 查找映射。cutover 不解码现有头像；有权限的头像读取可从归档点读原 base64。头像文件化是另一个 opt-in、分批、容量预检的任务。严格首错停止：在 stderr 即时打印失败阶段、脱敏记录标识、错误码和回滚结果，退出非零，不处理后续记录、不自动重试、不吞异常；详细 stack、受限 key/path、源/目标摘要及空间统计写入私有 `dataRoot/_migration-logs`（目录 0700、文件 0600、大小有界且预留容量）。不得记录密码、salt/hash、SMTP 凭据或内容。日志/journal 写入失败也立即停止。进程异常退出留下未决 journal 时所有版本均拒绝启动，须显式 `--rollback` 并核验后才可启旧版。

cutover 前失败回滚 SQLite 事务/sidecar；`user:` KV 源文件不改写，归档的源文件原子 rename 回 `_storage`；头像从归档 key 或 hash 已验证的新文件恢复，随后只删除本次创建且 hash 未变化的头像/DB 文件。核验恢复后旧 KV 摘要与 dry-run 一致才解锁。账号数量、字段、accountId、头像和 manifest 全部校验后才原子切换 storage marker；验证期间不开放写流量。全流程不复制同卷 70 GB 用户目录。
- 迁移期间不双写；迁移错误按上一步的 SQLite 事务与资源级 journal 回退。cutover 后若要回退旧版本，必须停新服务，先对 SQLite 与头像执行 `--rollback` 导出到旧 KV 格式并进行完整性验证，再原子切回 legacy marker；错误时继续保持 SQLite 为权威，禁止旧服务启动。回滚只写账户元数据和头像 key，不遍历用户数据目录；头像逐条流式转换，空间预检包括最大临时 KV 文件。保留 SQLite 文件至旧版验证完毕。全盘故障快照单独安排在其他物理设备，不要求同卷快照；回滚后另验证 SMTP/生命周期任务与备份任务状态。管理员 `recover.js` 使用同一 Adapter 或明确提供同等离线恢复路径。
- 将 `engines.node`、Docker 基镜像、CI 版本矩阵、本地运行指南、Linux/Windows 冷升级冒烟及测试运行时一起更新，删除“Node 20 可支持账户 DB”的模糊说明。

### 6. 上游同步和生产放行

- 在每次上游同步时重做差分检查：`users.js`、CLI、私有/public/admin Router、server 启停/关闭/上传追踪、设置/角色副作用、`request.user.profile/directories`、`getUserDirectories()`、种子索引及前端脚本入口/扩展时序。
- 回归现有 `/get`、`/delete`、`/backup`、`/me` 请求、权限、状态码和响应；增加旧扩展上下文/文件路径 smoke、旧 base64 列表响应兼容、新分页/单图授权、legacy avatar 归档回退、SQLite/KV cutover 和回退；验证用户 ZIP 仅含已文件化头像的明确迁移期契约与同名账号重建。
- CI 建 Node 22.13 与 24、Ubuntu XFS reflink 与不支持 reflink 的文件系统测试、Windows（clone 回退）测试；以干净构建验 `/lib.js`、登录、真实文件复制和 SQL migration。运行全 Jest/lint 与云升级/回滚数据用例。
- 仅在全部阶段门通过后，在有明确文件系统监控的单实例灰度部署；通过 300 用户 CoW 90% 阈值，运行一段观察后启用存量工具。任何种子校验、空间预检、资源级 rollback、API 行为、token 等价、租户隔离或清除保护失败均阻止推广。全盘灾备另行安排并尽量使用独立介质；不能为节省迁移时间在 80 GB/70 GB 使用场景要求同卷完整复制。

## 阶段依赖

1. 第 0 阶段先建立语义样本和量测工具。
2. 第 1 阶段不依赖 SQLite；优先单独交付资源占用改进及证据。
3. 第 2 与第 3 阶段可以分别开发，但同一版本放行时均需等价性验收。
4. 第 4 阶段头像文件化和第 5 阶段账户 SQLite 使用同一停服 migration journal 和资源级回退，不复制用户目录；全盘灾备另存其他介质，不作为本地迁移前提。
5. 第 6 阶段是每次同步上游及生产发布共同的门禁。
